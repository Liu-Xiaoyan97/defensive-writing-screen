# Defensive Writing Screen

This skill requires no other skill. Read its bundled `references/rewrite-guide.md` directly; do not load or defer to another writing skill. Upstream names record provenance, not a runtime dependency. User instructions and applicable project rules retain priority.

Default sequence: **control gate → Jev triage → agent verification → suggestions**. File edits need explicit authorization. A probability is a routing signal, never an editing permission or a confirmed defect.

## SOP

1. **Scope and authority.** Identify the draft, genre, language, authorized sections and output. Record its version or hash. Read only relevant context and available evidence. Do not invent results, causal links or restrictions. Calibration records in this skill stay generic: no project content, document identity, or draft excerpts. Runtime state and reports may contain the user's draft; keep them outside the skill package.
2. **Prepare units.** Use `scripts/prepare_units.py --candidates` or equivalent extraction retaining line ranges and original text. `.tex` selects the conservative LaTeX mode; use `--format latex` for stdin. Keep abstract, authorial captions, lists and prose around equations; omit mathematical displays, table cells, bibliography and layout commands. Inspect extraction coverage against the source. The script does not expand macros, includes or arbitrary TeX; report unsupported constructs and read them directly. Candidate spans are retrieval hints, not grammatical analyses.
3. **Structure check.** Use `scripts/check_structure.py`, then read section transitions. Report S1 missing conclusion, S2 ending on limitations, S3 missing necessary scope statement, S4 absent/folded related work, S5 evidence distant from its claim, S6 redundant implementation detail inside a review. These are document-level observations, not automatic defects. Genre and venue determine required roles. Research positioning at the end of related work is legitimate. Give a concrete reason and destination for any proposed move.
4. **Control gate.** Load the exact four active questions and all six controls from `references/controls.json`; `references/questions.md` explains the contract. Prefer `scripts/run_screen.py gate --out gate.jsonl`: a single invocation with a process pool of four, workers claiming units as they free up, retries on transport errors, and the resolved model recorded from each response. Because results return in completion order, the gate matches every row to its control by id; a run that reports a control under another control's scores is a script defect, not a classifier result. Fall back to individual tool calls only when the script cannot reach a service. Run one control per request using the same state shape as the draft. Each of four positive controls must reach its designated dimension at 0.65 or above; both neutral controls must be at or below 0.20 on every active dimension. Record all values and requested/resolved model identifiers separately. Also review the semantic challenge cases in that file; they test agent decisions, not classifier separation. Do not silently change questions, labels, controls or thresholds to pass. A control call may be retried once for a transport error, not for an undesirable score. A completed failing gate blocks draft Jev calls for this run and switches to the explicitly reported agent-only diagnostic mode below. Any question development belongs to a separate calibration run, not this document audit.
5. **Jev triage.** After a passing gate, prefer `scripts/run_screen.py triage --units units.jsonl --out screen.jsonl`, which asks all four questions per unit and writes each finished row to disk immediately, so a crash or an interrupted worker keeps the completed work. Units are claimed from one queue by a process pool (`--workers`, default four; `--executor thread` where forking is unavailable). Call the script once; the agent does not relay individual Jev requests. Use `--resume` to retry only failed ids instead of re-calling successes. Then hand over one packet: `scripts/run_screen.py summarize --screen screen.jsonl --units units.jsonl --out packet.md --sample 12` writes the units at or above the threshold plus a miss-check sample, each with scores, line ranges and exact text. The script absorbs the Jev traffic precisely so the agent can spend its attention on judgment rather than on relaying responses. Spend it: for every packet unit read the neighboring paragraphs from the source, decide sentence by sentence, and apply the protection and disposition tests below before writing a finding. Do not re-read the whole document and do not write a per-unit ledger. Otherwise ask the four questions together, one paragraph per request. Use exact questions from controls.json. Read the aggregate `screen.jsonl` rather than routing dozens of raw responses through the conversation. Script-mode and tool-mode values are not interchangeable: the same gate scored within about 0.04 of each other across the two paths, so keep one path per run and record which was used. The service returns a resolved model identifier; record it instead of writing unknown. Translate markers and create a matching control set before auditing a different language; report it as a separate question variant, never inherit English gate validity. `scope_tail` is retired from default routing in 0.11.0 after failing controls; repetition is also agent-side only. Neither is a zero-valued probability. For deterministic candidate spans and any proposed deletion, obtain the focused `removal_preserves` judgment with whole-paragraph context and known evidence, preferably through `scripts/run_screen.py focused --spans spans.jsonl`; retain exact spans and raw values. It tests deletion, not whether equivalent restructuring is permitted. Retry a failed call once; record persistent failures as `untriaged_error` with null values.
6. **Choose the review scope, then verify.** `triage_probability` is the maximum of the four active values. Select one scope before reading and report it. `screened` reads every routed unit (>=0.65), every focused candidate, the 0.45-0.65 band when it is small, and a stratified sample of the remaining units: all of them when there are 20 or fewer, otherwise at least 20 spread across the document, labeled in the record. `full` reads every unit and is required when the user asks for exhaustive review, when the draft is being accepted for publication, or when Jev was not used. In `screened` mode, count the misses found in sampled non-routed units and report that observed rate with the sample size instead of claiming recall. Low scores mean `not_selected`, not clean, and an unsampled unit stays unread in the report. Keep null for unrun/failed judgments. Read the bundled guide before proposing a revision. Protect P1 results/directions, P2 proof conditions, P3 measurement/reproduction conditions, P4 intervention scope, P5 design premises, P6 comparison semantics. These protect meaning, not exact wording: retain facts while independently judging framing. A clear ranked comparison is not defensive just because its numbers appear elsewhere. Read the whole paragraph and neighboring context before judging a backward reference; do not demand repeated conditions in every sentence. With insufficient context, keep the qualifier or request clarification rather than delete it.
7. **Record independent findings, including dispositions.** Each read unit has a summary verdict plus a `findings` array with separate exact spans, rule/action IDs, protection classes, reasons and proposals. Multiple R rules may apply to different spans in one unit, and every sentence of a read unit is inspected even after the first finding. Each routed unit also needs one line naming the dimension, the score and why it ended as a finding or a keep. R1 vague weakening, R2 concessive/self-undermining framing, R3 empty disclaimer, R4 empty contrast, R5 redundancy without a navigation/inference role, R6 genuinely empty retreating qualifier. R6 requires evidence that no restriction, uncertainty or useful contextual reference is lost; deictic wording alone is not enough. Narrative actions: N1 restate emphasis without changing rank, N2 narrow unsupported claims (not all interpretations of numbers), N3 relocate with a named receiving location. Keep categories K1 definitions, K2 results, K3 conditional baselines, K4 constraints, K5 scope, K6 meaningful contrasts, K7 captions/roadmaps. A revision must keep the modal strength and degree of the original: never soften "could hardly", "cannot", or "no prior report" into "difficult", "may not always", or "few reports", and never strengthen a warranted uncertainty into a claim. If the only available revision changes that strength, the verdict is KEEP. Prose compression and sentence merging are not defensive-writing findings; label them optional and never count them as detection.

A finding is `confirmed` when the bundled guide lists the construction as a rewrite rule, the revision preserves every fact, and the current wording weakens a supported claim or a supported unfavorable result through framing rather than content; a concession whose facts all survive is therefore confirmed, not optional. A finding is `optional` when the text is not defensive and the change is presentation: restating an already clear condition, importing numbers from a table, merging sentences, or reordering material. Structural observations are not span rewrites.
8. **Spend the packet, report only what carries risk.** The response records findings, one line per high-risk packet unit, one line for the miss-check sample, structure observations and cost facts. Cite the packet file instead of copying its scores or rebuilding its table; the script already wrote the machine record, so the skill writes no per-unit report of its own. Capturing a finding matters more than shortening the response: a finding below the threshold is recorded whenever it exists, because a low score never suppresses an observed problem, and a read unit without a finding appears only in the aggregate count. Report what the extra verification changed, such as a unit kept because its neighbors resolved a reference or a finding confirmed only after reading the surrounding argument. Focused checks are not optional: every deterministic candidate span and every proposed deletion needs its `removal_preserves` value before the finding is reported, and `findings.json` states which spans were checked, which failed and which were skipped. When a required check did not run, the footer names it under `not_run` and the finding is limited to a rewrite, never a deletion. In Jev mode, state how each item was reached (routed, focused, sampled, direct review); a low score does not veto a separately justified finding, and a deletion needs a high focused value plus agent verification. In agent-only mode, deletion suggestions must state that Jev validation is missing. Keep null for failed judgments and report failing ids. Compute precision only over genuinely routed units and agreement only against independent labels. Report cost as measured facts separate from quality: scope, units read and unread, Jev requests with retries and failures, and agent turns or tokens when exposed. Do not call a Jev-first run cheaper unless a measured comparison on the same draft supports it: a run that also reads every unit cannot save agent work by construction. Write any full per-unit table to a file artifact and reference it; never inline it. Suggestions alone do not authorize edits; after authorized edits verify numbers, units, direction, conditions and source integrity, then rerun the applicable checks and say what did not run.

## Working without Jev

No caller, a completed failing gate, or a persistent gate transport failure triggers **agent-only diagnostic review**. Do not tune during the audit. Continue steps 1–3 and 6–8, using all bundled rules and semantic challenge cases. Mark every draft probability null and use `untriaged_no_caller`, `untriaged_control_failed`, or `untriaged_error`. Report why Jev was skipped; never call this a successful Jev workflow. Partial draft failures may coexist with successful records but overall screening is incomplete. Infrastructure failures and classifier failures are different outcomes.

## Reporting

Compress the response to the two things a reader acts on: the original text and the revision. Write it in controlled technical English, following the discipline of ASD-STE100: one idea per sentence, short sentences, approved simple words, active voice, no hedges, no restatement, no justification prose. Move reasons, kept facts, protection classes and per-unit notes into `findings.json` and cite the file.

Fixed response shape:

```text
skill 0.17.0 | target <sha256> | units <n> | routed <n> | sampled <n> | failed <n> | model <name>
L<line> | <original sentence, verbatim> | <revision, or KEEP> | <rule/disposition code>
...
sample <hits>/<n> | findings <n> confirmed, <n> optional | checks <ran> | <not run>
```

Rules for the response:

- One finding per line. No paragraph explains another line.
- Use the codes `R1`-`R6`, `confirmed` or `optional`, and `KEEP`. Do not spell out arguments.
- Do not quote the packet, its scores, or the document's context. The line number locates it.
- Do not write sentences about the paper's quality, the method, the process, or the review itself.
- A line longer than the original plus its revision is too long. Cut the extra words.
- Report counts, not narratives: review scope, units read, units unread, sample hits, failures, checks run.
- Ask for the full explanation only when the user asks for it, then read it from `findings.json`.

Compression never removes a finding, a number, a metric direction, or a condition from the revision itself. It removes prose about the finding.
